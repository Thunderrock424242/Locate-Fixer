# Locate Fixer 4.0 validation

Validation date: 2026-10-10. Branch: `codex/locate-fixer-4-safety`.
Base: `origin/1.21.1` at `69243355068be690400c4b64a1b313d6b598c7c5`.

This is a development candidate. All four target builds and automated regressions
pass. Isolated NeoForge dedicated-server checks also pass for the cases below,
including TerraBlender/Biomes O' Plenty. Player travel, multiplayer, the original
issue-89 modpack and broad comparative performance acceptance remain unverified.
No existing user world or published release was changed.

## Isolated dedicated-server checks

All running NeoForge smoke servers were stopped with normal save/shutdown after
validation. Their disposable worlds, scripts and captured logs remain ignored
under `build/smoke/` and `build/audit/`; they are not distributed with the mod.

The vanilla-world NeoForge profile used Java 21, NeoForge 21.1.230, one worker,
queue capacity 32, a 120-second timeout and stages `[128,512,1536]`. The world seed
was `4401357362987183368`, with view/simulation distance 3 and no players. The
later runs bound only loopback addresses. These small stages were deliberately
chosen for bounded smoke checks; they do not benchmark the larger default limits.

| Check | Observed result |
| --- | --- |
| Dedicated server start/stop | Reached `Done`, commands usable, normal saved shutdown. |
| Vanilla biome | Plains found at `[-192,72,-224]`; exact repeat used memory cache with zero backend searches. |
| Vanilla structures | Plains village and ancient city returned native generator coordinates. |
| Unavailable dimension | Nether plains was `UNAVAILABLE`; no radius search. |
| POI absence | Home was `NOT_FOUND` in the new world; a live occupied-POI success case remains pending. |
| Invalid target | Misspelled `minecraft:stronhold` suggested `minecraft:stronghold`. |
| Explicit teleport from console | Rejected as requiring a player before submitting travel. |
| Native result callback | `/execute store result ... run locate biome minecraft:plains` stored distance **316**, rather than asynchronous admission value 1. |
| RCON response | After adding native RCON fallback, ordinary locate returned coordinates in its response packet. |
| Datapack `/reload` | Cancel/clear hooks left zero cache/index/history entries; the next query was a miss. No custom datapack replacement was tested. |
| Saved index/restart | A discovered entry survived normal shutdown/restart; history/cache began empty and an index candidate still caused live nearby-first search. |

The TerraBlender profile used NeoForge 21.1.230, TerraBlender 4.1.0.8,
Biomes O' Plenty 21.1.0.13 and GlitchCore 2.1.0.0, with a separate new world and the
same seed/resource limits. It reached `Done`; TerraBlender registered the BOP
overworld and Nether regions. The asynchronous console search found
`biomesoplenty:lavender_field` at `[704,67,896]`, distance 1120. Native RCON locate
returned the same coordinates. In the Nether the same target was `UNAVAILABLE`,
with one availability call and zero backend searches. Final normal output had a
simple start line and coordinates, with no stage/count chatter.

That modded profile also logged BOP ocelot-category warnings and an allay spawn
placement warning. Development refmap warnings occurred for the worldgen mods.
These are reported as profile context, not a clean-log or whole-modpack claim.

Forge 1.20.1's Java-17 dedicated development launcher booted the loader but stopped
at the Minecraft EULA gate. No agreement was written or bypassed. It did not reach
world startup, so Forge live commands and compatibility are unverified. The
development classpath warned about its refmap; the inspected **production** Forge
JAR contains the required mappings. Fabric dedicated-server/client launches and
installation of the production JARs were not tested.

## Measured performance and limits

These are individual observations on small, empty local test servers. Times are
integer milliseconds from diagnostics, rounded down. Warm generator/JVM state,
different API paths and differing measurement windows prevent a controlled
before/after comparison.

| Query/context | Job wall time | Total / longest server call | Cache / index | Longest overlapping tick interval |
| --- | ---: | --- | --- | --- |
| Initial plains lookup | 36 ms | 20 / 11 ms | miss / miss | Instrumentation not yet installed |
| Exact repeat plains | 0 ms | 0 / 0 ms | hit / unused | Instrumentation not yet installed |
| Initial plains village | 675 ms | 671 / 670 ms | miss / miss | Instrumentation not yet installed |
| Plains after server restart | 36 ms | 19 / 12 ms | miss / hit | 43 ms, 2 samples, none over 100 ms |
| Ancient city | 139 ms | 128 / 124 ms | miss / miss | 127 ms, 4 samples, 1 over 100 ms |
| BOP lavender field | 477 ms | 446 / 309 ms | miss / miss | 309 ms, 4 samples, 2 over 100 ms |
| BOP lavender field in Nether | 0 ms | 0 / 0 ms | unused / unused | 50 ms, 1 sample |

For reference, the subsequent native RCON BOP search logged 189 ms inside native
locate (195 ms RCON round trip). It ran after the asynchronous search and used a
different radius/path; it does **not** establish a speedup or slowdown.

Native recent-tick snapshots could show only 0.13–0.18 average MSPT and miss locate
work executed between tick bodies. This observation prompted separate elapsed
tick-interval capture using the existing job/tick owner. It retains at most 256
job references until the next tick and is enabled only with benchmarking. The
127 ms and 309 ms intervals demonstrate actual delayed tick cadence during these
searches. Intervals also include scheduling and other server work; they are not
exclusive CPU attribution. Neither job wall time nor a later 100-tick snapshot
proves the search was nonblocking.

World operations remain serialized. A queued call can be cancelled and worker
waits are bounded, but an already-executing vanilla generator call is not safely
preemptible. Structure placement searches and 32/64 biome sampling preserve native
API semantics rather than an exhaustive mathematical nearest search. Native
structure Y can be a placement coordinate (the ancient-city result was Y=0), not
the center of its generated rooms. Travel searches near that supplied height and
can fail or use a safe surface alternative; an underground fixture does not prove
live arrival inside every underground structure.

CPU, process memory, chunk generation/loading counts, index persistence cost and
multi-player queue/tick behavior were **not measured**. The 3.1.0 release was not
run as a comparative baseline. No numerical overall performance improvement is
claimed.

[Issue #89](https://github.com/Thunderrock424242/Locate-Fixer/issues/89) was reviewed
with its attached crash and log. The report used Minecraft 1.20.1, Forge 47.4.20,
Ixeris 4.6.5 and `locatefixer-3.1.0.jar`. The crash reports an invalid locate
injection target and no loaded refmap. Ixeris's presence in the mouse-event stack
does not prove a thread conflict. Current production Forge mappings were verified;
the original pack and 47.4.20/Ixeris combination were not reproduced. No speculative
Ixeris patch was added.

## Remaining release acceptance

Before publishing, test the matching production JARs on every loader with real
players. Cover ordinary locate and explicit travel, permissions and orientation,
occupied POIs, rare modded structures, multiple simultaneous players, cancellation
and timeout during loading/countdown, overlapping destination tickets, disconnect,
shutdown, Nether/End/custom-height dimensions, world borders, underground landing,
mod-adjusted teleport events and unchanged world blocks. Replace a datapack or
worldgen configuration and verify stale state cannot escape reload.

Run the original issue-89 pack and the listed compass/async/performance mods.
Compare vanilla, 3.1.0 and this candidate under equivalent cold/warm worlds and
search limits, measuring tick cadence/MSPT, CPU, memory, queue pressure, chunk
work and save cost. Existing automated fixtures and the isolated checks above
provide regression evidence, not release acceptance for these missing cases.
